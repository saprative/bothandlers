## Purpose

Defines how BotHandlers counts what a customer pays for: active human seats, the shared organization-wide intervention capacity those seats fund, and the strict boundary between provisioned directory users and billable seats.

## ADDED Requirements

### Requirement: An active seat is an explicitly enabled paid membership

A seat SHALL be billable only when a human membership in the organization is explicitly assigned an enabled paid seat. Seat status MUST be an administrative decision, never inferred from behavior.

#### Scenario: Seat statuses are counted

- **WHEN** the billable seat count is computed for an organization
- **THEN** memberships with an active paid seat status are counted, and memberships with viewer or disabled seat status are not

#### Scenario: An active seat is never used

- **WHEN** a membership holds an active paid seat but the person never signs in or responds during the billing period
- **THEN** the seat remains billable for that period

#### Scenario: A person responds without an active seat

- **WHEN** a membership whose seat status is viewer or disabled participates in the period
- **THEN** it does not become billable as a result of that participation

#### Scenario: Seat count is not derived from activity

- **WHEN** billable quantity is determined
- **THEN** it is derived solely from enabled paid seat assignments, and never from sign-ins, responses, or monthly active users

### Requirement: Directory provisioning does not create billable seats

Provisioning a user into the organization's directory SHALL NOT by itself make that user billable. Seat assignment MUST be a separate, explicit action.

#### Scenario: A large directory is synchronized

- **WHEN** an enterprise directory synchronization provisions several thousand users into an organization
- **THEN** the billable seat count is unchanged until seats are explicitly enabled for specific memberships

#### Scenario: A provisioned user is granted a seat

- **WHEN** an administrator enables a paid seat for a provisioned membership
- **THEN** that membership becomes billable from that point

#### Scenario: A user is deprovisioned upstream

- **WHEN** a user is removed from the upstream directory
- **THEN** their membership seat is disabled and ceases to be billable, while their historical decisions and audit records remain intact and attributable

### Requirement: Intervention capacity is a shared organization-wide pool

Each paid seat SHALL contribute intervention capacity to a single pool owned by the organization. Capacity MUST NOT be partitioned per user.

#### Scenario: Capacity is computed

- **WHEN** an organization holds twenty active seats on a plan granting one hundred and fifty interventions per seat
- **THEN** the organization has a single pool of three thousand interventions for the period

#### Scenario: Consumption is uneven across responders

- **WHEN** one responder handles five hundred interventions in a period while others handle few
- **THEN** all are drawn from the shared organization pool and no per-user limit blocks that responder

#### Scenario: A seat is added mid-period

- **WHEN** an additional paid seat is enabled during a billing period
- **THEN** the organization's pooled capacity increases accordingly

### Requirement: Only intervention workflows consume metered usage

Usage SHALL be counted per intervention workflow. Operational activity generated by the platform in service of that workflow MUST NOT be metered.

#### Scenario: One intervention generates extensive activity

- **WHEN** a single intervention produces multiple notifications, escalations, retries, webhook delivery attempts, audit events, and status polls
- **THEN** exactly one intervention is counted against the pool

#### Scenario: Non-workflow activity occurs

- **WHEN** an organization makes API calls, receives notifications, incurs retries, has webhook attempts delivered, or accumulates audit events
- **THEN** none of these increment metered usage

### Requirement: Connected agents are not billed per agent

Registering agents SHALL be encouraged rather than penalized. On paid plans the number of connected agents MUST NOT affect price.

#### Scenario: An organization registers many agents

- **WHEN** an organization on a paid plan registers a large number of agents
- **THEN** no additional charge results from the agent count and no agent registration is refused on billing grounds

### Requirement: Exceeding included capacity never blocks human escalation

When an organization exhausts its included intervention capacity, the system SHALL continue to accept, route, page, and resolve interventions, metering the excess as overage.

#### Scenario: The pool is exhausted mid-period

- **WHEN** an agent creates an intervention after the organization's included capacity is consumed
- **THEN** the intervention is created, routed, and paged normally, and the excess is recorded as overage

#### Scenario: A critical escalation arrives past the limit

- **WHEN** a critical intervention is raised by an organization in overage
- **THEN** it is processed with no degradation to routing, notification, escalation, or delivery

### Requirement: Organizations are warned before capacity is exhausted

The system SHALL notify organization administrators as consumption approaches included capacity, so that exhaustion is anticipated rather than discovered.

#### Scenario: Consumption crosses a warning threshold

- **WHEN** an organization's period consumption crosses a defined warning threshold below its included capacity
- **THEN** organization administrators are notified, with remaining capacity stated

#### Scenario: Capacity is exhausted

- **WHEN** included capacity is fully consumed
- **THEN** organization administrators are notified that subsequent interventions are metered as overage
